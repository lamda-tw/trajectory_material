# 总体研究设想：固定评价标准下的 Agent 自改进

更新：2026-10-09。这是一份长期路线图，包含条件成立后才考虑的设计；当前工作以 [README.md](/root/autodl-tmp/workspace-tw/plans/2026-10-08_rubric_research/README.md) 为准。以下没有新实验结果。

## 1. 先把研究问题收窄

当前最值得问的是：

> **DRACO 的固定规则，能否可靠评价 Qwen3-8B 的轨迹行为，并提供有助于完成任务的训练信号？**

如果这个基础成立，再进一步研究：

> **在评价规则保持固定时，学生能否根据自己的规则失败，生成可验证的修复，并把修复逐步内化为其他任务上的自主行为？**

这样形成一个自然的故事：先建立稳定的评价标准，再让学生根据这个标准改善自己。前期变化的是学生行为与训练数据；评价规则先保持不变，便于判断究竟学到了什么。

静态规则仍需要模型应用到具体上下文，因此不能消除 judge 的全部影响。但它能固定外部模型的工作范围：首版 Codex 只做判定，不负责发现新标准、提出训练课程或编写正确动作。

当前保留两个初始化系列：原始 [Qwen3-8B](/root/autodl-tmp/models/Qwen3-8B)，以及用户指定的现有 train90 / epoch5 SFT LoRA。每个系列内部的方法对照从同一个起点独立开始；同一方法的多轮自改进才延续自己的 checkpoint。LoRA 已含历史 Codex 监督，不能把这一系列称为无教师起点。具体对照、训练参考策略和预算见 [实验计划](/root/autodl-tmp/workspace-tw/plans/2026-10-08_rubric_research/EXPERIMENT_PLAN.md)。

## 2. 为什么从静态规则开始是合理的

DRACO 已比较静态/动态规则、有/无步骤 credit，并报告其设置下静态奖励较早饱和。因此，静态规则加 GRPO 是有依据的基线，也不是新的论文贡献。[DRACO 原文，§4.1、§4.3–4.4](https://arxiv.org/html/2609.04094v1)

还需要避免一个过强的区别：官方仓库已有 self-judge 设置，并随 policy adapter 刷新 judge。因此不能声称 DRACO 完全没有迭代或自身模型参与的机制。我们拟增加的是经验证的学生修复、帮助撤除及训练方式分配，是否形成新贡献仍需逐项对照。[官方代码说明](https://github.com/IBM/draco/blob/cfafd0f81f2c49aa36a4b25a2a7b6ac6e119f47b/README.md)

对我们而言，原始 Qwen3-8B 在当前环境中的起点、常见错误和评分覆盖率需要重新测量。不能直接把其他模型上的动态规则收益当成增加复杂度的理由。

这一顺序能分别回答：

| 阶段 | 本次只增加什么 | 要回答的问题 |
| --- | --- | --- |
| A：静态评分 | 官方 21 条规则和轨迹判定 | 规则能否可靠区分实际行为 |
| B：最小 GRPO | 按官方流程计算静态奖励 | 评分能否产生有用的参数更新 |
| C：筛选 SFT 或步骤 credit | 二选一，依据 B 的问题决定 | 是监督目标不足，还是更新位置过粗 |
| D：固定规则提示下自修复 | 学生重新尝试同一步 | 学生能否产出更多可用训练目标 |
| E：多轮自改进 | 重复执行、修复、训练、复评 | 增益能否积累并迁移 |
| F：按需扩展 | OPD、收益调度或动态规则 | 是否解决前面已观察到的瓶颈 |

后续阶段不是必须全部实现的清单。若一个简单组合已经形成清楚结果，就围绕它写论文，不为凑齐 SFT、OPD、RL 而继续堆叠。

## 3. 第一版直接采用作者的 21 条规则

采用 [DRACO 官方静态文件](https://github.com/IBM/draco/blob/main/training/rubrics/static_rubrics_qwen36_27b_mece.json)，保留每条的标题、描述和具体判分说明。文件中的历史通过率、失败率只反映作者的数据，不作为新实验的权重。

先核对工具协议是否兼容，冻结规则和 judge 提示。此前三条粗分类不再作为训练评分表。等观察到稳定错误模式后，再讨论这些具体规则怎样归入能力维度。

评分粒度遵循官方流程：**每条完整轨迹、每条规则，得到一个 PASS/FAIL/NA。** 当前没有“每步独立打 21 个分”的矩阵。轨迹级判定需要结合整个过程，例如短暂报错后正确恢复，可以满足恢复要求。[官方奖励流程](https://github.com/IBM/draco/blob/main/training/docs/REWARD_PIPELINE.md)

后续开启步骤归因时，再把规则结果与相关动作联系起来。整条轨迹通过某项规则，不保证中间每一步都通过该项局部检查；未被引用的步骤也不能直接当作失败步骤。

## 4. 最小训练沿用静态 rubric reward

第一版无需教师替代动作或分布蒸馏，直接使用作者的静态奖励流程。每任务采 6 条轨迹，逐轨迹评分后，在组内去掉没有任何 FAIL 的规则，再计算：

    r = (保留且适用的 PASS 数 − FAIL 数) / (PASS 数 + FAIL 数)
    R_train = 10 × r

NA 不进入分母；分母为空时记 0。全部 FAIL 的规则保留，但组内 reward 相同时仍没有相对优势。公式、过滤与缩放说明见 [实验计划](/root/autodl-tmp/workspace-tw/plans/2026-10-08_rubric_research/EXPERIMENT_PLAN.md)。

拟比较官方结果奖励 GRPO 与纯静态 rubric GRPO；两份初始采样已完成，LoRA 已做 12 条静态评分 smoke 及同批校准重测，校准仍暴露执行证据误读。当前按用户要求回到官方静态基线，只做必要协议适配，停止逐题增加 judge 约束；另准备三个未参与校准的 train 题检查（已恢复评分，最新执行结果见 README），允许并披露普通判分噪声。LoRA 的静态 GRPO 单次工程更新已完成；正式多轮训练和 outcome 对照尚未执行。移除先前自行提出的 0.2 混合权重。静态分支不使用官方结果作为训练 reward，官方结果单独用于观察和 dev 验证。

先用标准轨迹级 GRPO，不加步骤 credit。模型使用我们的 Qwen3-8B，因此这是采用原静态流程的基线，不是原论文数值复现。

重点检查两件事：组内奖励是否有区分度；规则分数上涨是否伴随完整任务成功率改善。训练中不因曲线不好看而静默修改规则、权重或过滤方式。跨轮统计保留固定 21 条的原始判定，不能只比较各组筛选后剩下的规则。

## 5. SFT 怎样接：先分清轨迹选择和步骤选择

轨迹级判定不能直接变成逐步正确动作标签。最简单的 SFT 后续实验，可以在本次学生生成并官方验证成功的 train 轨迹池中，比较普通成功轨迹 SFT 与按静态 rubric 表现筛选轨迹的 SFT；匹配监督 token 预算，报告数据覆盖与重复使用量。

这一实验回答规则是否帮助选轨迹，还没有回答怎样选择关键步骤。若要做步骤 SFT，先增加步骤定位和相应的局部检查；一个 step 被某个全局 PASS 引用，也不能自动保证它在所有方面都是正确示范。

输入始终是该动作前的真实历史，工具观察与 judge 判定不计算标签损失。dev 的轨迹、答案和修复不进入训练池。

若原始模型暂时缺少足够成功轨迹，就暂缓筛选 SFT。后续自修复可以提供新样本，但不为了填满数据池默认让 Codex 批量写答案。

## 6. 如果规则有用，下一步只加一个机制

出现不同结果，对应不同扩展：

| 初步结果 | 下一步更值得做什么 |
| --- | --- |
| 评分可信、GRPO 提高自主成功率 | 扩大任务与种子，确认收益稳定 |
| 评分可信，但轨迹奖励把局部差异平均掉 | 在相同 reward 下比较有/无步骤 credit |
| 有成功样本，但 GRPO 更新不稳定 | 先比较成功轨迹 SFT 与规则筛选 SFT |
| 大量相同规则失败，缺少可用正例 | 让学生收到固定规则提醒后尝试自修复 |
| 规则通过率很高，实际失败仍很多 | 检查缺失的行为要求，再考虑扩充静态规则 |
| 训练任务改善，其他任务没有改善 | 优先检查泛化与信息泄露，而非增加复杂度 |

步骤 credit 可参考 DRACO，但在这个实验中应固定规则、奖励和数据预算，只改变 credit 分配。这样才能知道收益来自哪里。

## 7. 最值得保留的长期故事：规则不变，学生自己产生下一轮教材

当固定评分和至少一种训练方式已成立，可以加入一个很小的自修复循环：

    自主执行
      → 固定规则判定 fail，再定位可干预步骤
      → 给出这条规则，学生重试
      → 验证修复
      → 对修复动作做去提示 SFT
      → 在其他任务无提示复评
      → 再次自主执行

先只用 SFT 接通循环。GRPO 若已验证有效，可以作为固定的整任务训练环节；OPD 此时仍不是必要条件。

这版可以进一步限制 Codex 的参与：评分与步骤归因阶段给出规则 ID 和相关位置；确认位置可局部干预后，修复提示由模板拼接原规则生成，例如：

> 请按“获取完整数据”这条规则重新检查：当前决策所需记录是否已经取全，是否遗漏后续页或必要详情。

首版不让 Codex 另外写自由形式的解释或修复代码。提示只进入修复尝试，训练输入和最终评估输入都不包含该提示。

同时做相同采样预算的无提示重试，排除“多试一次就碰巧成功”的解释。

### 怎样验证一个修复

从原动作执行前的真实环境恢复，替换这一步，再由冻结学生无提示续跑。主版要求局部规则通过且官方任务成功。单次分支成功说明这次修复有效，不说明该能力已经掌握。

环境恢复必须包括数据库和解释器状态；报错可能发生在副作用之后，不能假定失败动作完全没有执行。已有分支重放工程可以复用，但模型和数据来源要重新检查。

这一步借鉴 CSO 的验证思想；CSO 本身已包含 rubric 辅助筛选和迭代优化。因此论文要进一步检验修复如何被内化，而不是把“重复找关键步”写成新意。[CSO](https://arxiv.org/html/2602.03412v1)

### 三个设计保留为轻量版本

1. **能力档案先是一张表。** 每条固定规则的失败次数、覆盖率、无提示重试和提示修复计数，不训练分类器，也不预设复杂能力体系。
2. **修复池先是可追溯样本。** 保存原历史、规则 ID、学生修复动作和验证结果，不先做大型知识库。
3. **下一轮调整先用简单原则。** 优先关注经常失败且能得到有效修复的规则，保留少量其他样本防止遗忘。

只有简单策略出现明确瓶颈，才增加“训练方式 × 实际学习收益”的账本与受控微试验。昂贵的教学算子搜索不应成为第一版自改进的前提。

## 8. 怎样把这个方向发展成论文

候选题目：**From Fixed Rubrics to Self-Improving Agents**。

更具体的中心问题是：

> 在固定规则与受限外部教师参与下，能否让学生从自身错误中持续产生有用修复，并将修复转化为跨任务的自主执行能力？

静态规则提供一个持续可比的观察坐标。同一规则下可以依次测到：

- 原生执行是否容易失败；
- 规则提醒是否帮助学生修好；
- 去提示训练是否改善其他任务；
- 改善后是否还需要同样的帮助。

这保留了原先“修复收益与学习收益分开”的主张，但实现可以从固定规则加纠错 SFT 的两轮循环开始，不需要一次做完整调度系统。

正式论文至少需要区分：

| 对照 | 检验什么 |
| --- | --- |
| 只有评分与 RL | 自修复数据是否增加有效信号 |
| 相同预算的无提示重试 | 规则内容是否比额外采样更有价值 |
| 一次生成数据后反复训练 | 使用新策略持续生成修复是否重要 |
| 原任务重放与其他任务评估 | 学到的是修复记忆还是可迁移行为 |

如果后续确实使用多种训练方式，再增加统一 SFT、统一 OPD 和分配策略的对照。没有使用这些机制时，就不把它们写进论文贡献。

潜在贡献是对“固定规则怎样支持持续的自我监督与帮助撤除”给出清晰方法和证据。静态奖励、筛选样本、迭代自训练分别已有先例，组合的有效性与作用机制仍需实验支持。

## 9. OPD 和动态 rubrics 何时才值得加入

**加入 OPD 的条件：** 学生在规则提示下已经能产生可靠修复，但硬目标 SFT 的迁移有限。此时尝试由看到反馈的冻结 Qwen 提供分布，监督不看反馈的学生。SDPO 提供了反馈自蒸馏的已有依据；它不是本方案新发明的训练目标。[SDPO](https://arxiv.org/html/2601.20802v2)

必须与相同前缀、相同有效修复机会下的 SFT 比较，并明确学生新采样和教师冻结条件。Codex 没有 logits 不妨碍这种路线，但它仍带来实现与计算成本。

**加入动态规则的条件：** 固定规则已较稳定通过，新的失败却无法被原规则解释。先检查能否补充一条明确的静态规则；如果问题确实高度依赖任务和轨迹，再比较动态生成。

扩展时保留原来的固定规则作为评估锚点。动态 reward 的变化与固定标准下的进步分开报告，避免评分标准改变后无法判断学生是否改善。

**加入收益驱动调度的条件：** 已观察到不同规则或训练阶段对 SFT/OPD 的反应不同，而且简单分配明显浪费预算。再用少量受控训练测量无提示收益，而不直接实现大规模多分支搜索。

## 10. 与自改进文献的关系

- **BaT** 已将 rubric 诊断、课程选择、训练和复评组成循环，因此“加一层闭环”本身不足以区分。[原文](https://arxiv.org/html/2608.16211v1)
- **SOAR** 已用学生实际进步指导教学，因此未来若加收益账本，也要把学习进步控制视为已有思想。[原文](https://arxiv.org/html/2601.18778v1)
- **STaR** 已展示自产有效输出反哺训练的迭代路径。我们需要研究的是交互环境下的步骤修复、帮助需求和跨任务内化。[原文](https://arxiv.org/abs/2203.14465)

这些对照用于约束最终论文主张。当前无需同时复现所有方法；先证明最小信号和训练链路成立，再围绕实际有效的机制选择最近邻基线。

## 11. 所有尝试统一在官方 dev 上验证

按当前约定，所有实验都使用**同一套完整 AppWorld 官方 dev**比较，包括原始模型、两种 GRPO，以及以后可能加入的 SFT、OPD 和自修复方案。取消另选少量开发任务或临时划分保留集的安排。

统一 dev 任务清单、环境与工具版本、提示词、parser、解码配置、随机种子方案、上下文及最大执行预算。预先固定评估时点和 checkpoint 选择方式；若不同方法的训练或 judge 成本不同，连同结果一起报告。少量任务可用于调试，但不代替完整 dev 的正式比较。

训练 rollout、教师诊断、修复和梯度更新仍只使用 train。dev 的聚合成绩可以用于当前方法选型，不把 dev 的轨迹或正确动作回灌训练。当前先不使用 test；持续用于选型的 dev 成绩按开发结果报告。

验证时从完整任务起点自主执行，不提供额外 rubric 提示或教师修复。主要比较官方任务成功率与成本；当前 dev 不调用 rubric judge，规则表现来自 train 的独立诊断。

两个初始化系列分别报告训练前后的 dev 变化；方法间对照在同一初始化内进行，并对齐本轮新增预算。历史 SFT 的收益与本轮 rubric 的收益分开解释。当前文档只规划研究，不将预期提升写成结果。
