## 真实调用中发现并处理的问题

**输入解析。** 旧输入准备器无法处理 `302c169_3__03` 第 10 步的孤立通用围栏。新建 `prepare_input_v2.py`，按采集器原有规则提取实际 Python 代码；原准备器和 prompt v1 均保留。全部 540 条 base 轨迹通过输入检查，539 条原本兼容的输入逐字段完全相同，原来失败的 1 条恢复兼容；两条既有 SFT 输入样例也完全不变。全部 base 原始文件 SHA256 与采集索引一致。输入修复不代表重写学生动作。

**调用事件验收。** Codex 将“Code Mode 已被禁用”的提示输出为 error 类型的 item，旧验收器误认成工具使用。首次两条响应其实完整有效，错误验收触发的两个重试已取消。修复后只允许这一条特定提示；仍要求 completed turn，并拒绝其他未知工具事件。已有两条最早的有效响应直接复用，没有改写模型标签或挑选更喜欢的重试结果。

首次原始记录在 [v1_audit](runs/v1_audit/)，恢复后的六条统一结果在 [v1_audit_recovered](runs/v1_audit_recovered/)，新版在 [v2_audit](runs/v2_audit/)。共发起 **14 次调用：12 次有完整响应、2 次重试取消**。取消的调用没有完整 usage 事件，其消耗未知，不能按零计算。[调用问题记录](review/call_issue.json)

## Prompt 改动及版本保留

v1 保持原始内容和 SHA256。新建 [prompt_v2.txt](/root/autodl-tmp/workspace-tw/plans/2026-10-12_appworld_step_rubric/prompt_v2.txt) 和对应 schema，输出 `rubric_version=appworld-step-v2`。两版输入字节相同，模型与推理设置相同；都使用 audit 模式。

v2 增加五条通用边界，不加入具体题目、对象 ID 或正确答案：

1. 局部读取/筛选与全集证据消费分开，不把选择一个已见对象解释成声明全局唯一。
2. 已知读取执行失败不自动记为证据“不确定”；分别处理 R1 与 R2，保留适用性。
3. 登录和获取令牌通常不算 R5 的业务状态修改。
4. API 规格要求在不同轨迹间一致执行，包括 complete_task；协议违规本身不推出业务逻辑错误。
5. 分页判断依据本次可见接口规格或反馈，不能仅因返回若干条就假设存在隐藏页。

## 证据复核观察

本会话根据实际轨迹编写了 28 个开发检查点，在 v2 调用前冻结。部分检查点是在看到 v1 后制定的，且用于指导 v2，因此只能衡量本轮问题是否被修正，**不能称为独立人工金标准、评分准确率或泛化提升**。

| 指标 | v1 | v2 |
| --- | ---: | ---: |
| 完整且结构有效的轨迹 | 6/6 | 6/6 |
| 完整覆盖实际步骤 | 66/66 | 66/66 |
| 符合开发检查点 | 24/28 | 27/28 |

四处修正是：成功闹钟轨迹第 7、8 步的 R2 从 U 改为 P；失败闹钟轨迹第 10 步的 R8 与同类调用保持一致；成功歌单轨迹第 4 步不再将登录当作业务写入。v2 同时保留对真正需要全集的闹钟操作与结束声明的 U，没有利用官方成功标签把未知强行改成 P。

一个回退是：成功便签轨迹 `cf6abd2_2__01` 第 12 步，先前结果已经显示 Bucket List，学生仍声称找不到并按相同参数重复搜索。本会话复核认为 R6 应保留 F；v1 为 F，v2 为 N，R2 也由 F 变 P。提示对正常探索的保护可能过宽，但每版只有一次调用，不能排除模型随机性，也不能断言具体修改的因果作用。[未解决问题](review/residual_findings.json)

两版都正确识别了这些有明确证据的案例：

- 失败闹钟第 8—10 步：将 Wake Up 当作 go-to-sleep 目标修改；禁用循环只出现在未执行的第二代码块，最终却声称完成。
- 失败便签第 11—12 步：实际文本替换正确，R5 为 P；说明误读旧状态与最后未实际调用 complete_task 分别保留错误判断。失败轨迹包含有效操作。
- 成功歌单第 1、6、8 步：伪令牌和“三分钟一首”的错误假设仍被识别，后续按真实 duration 求和、取最大及修复得到肯定。成功轨迹包含应纠正的局部行为。

全部 528 个位置中有 43 个发生标签变化，不应把这 43 个全部称作改进。部分是适用性或错误归属变化：例如同一文本事实错误，有时只影响 R3，有时也影响 R4；恢复行为的结束边界也有 P/N 差异。28 个开发检查点并未覆盖所有位置。

R8 在 v1/v2 分别有 47/48 个 F，主要涉及未查看 API 完整规格。这是数据中的实际协议问题，但其高频率也说明：**不能把全部维度等权求和或只按 F 数量挑“最值得学习”的步骤。** 业务错误、协议问题、适用性和学习价值仍需区分。

这些是 CLI 返回的 usage；缓存属于输入中的子集，reasoning 属于输出中的子集，不能再相加。两条取消重试的消耗未包含在表内。没有据此推算货币费用。

大部分输出 token 被记录为 reasoning；短标签矩阵并不等于低推理成本。此轮没有运行 batch 模式或更低推理档位，所以不能声称删除短解释便能显著提速，也不能凭这六条、每版一次调用断言 v2 更快。

## 当前可用范围与后续问题

目前已经具备可追溯的逐步 judge 流程，能产生有证据的局部判断，并能发现与复核具体误判。**v2 保留为候选版本，尚未标为稳定批量评分标准。** 本阶段达到“用少量完整成败轨迹跑通、发现问题、版本化改进并回测”的范围。

下一轮优先处理“正常探索 vs 忽略已有证据的无效重复”边界，并在未参与本轮开发的完整轨迹上验证；若改 prompt，建立 v3。还应小规模测量同输入重评一致性和 audit/batch 标签一致性。当前没有启动这些扩展，不在本轮开发样本上持续改到满分。

原集合中约 52.8 万字符的长输入未纳入此六条，长输入、更多应用与任务类型、全量吞吐仍需另行验证。输入准备器目前仅对结构化 password/token 字段识别到的值做一致替换，裸打印凭据可能保留；它不是通用秘密检测器。所有判断仍仅基于提供的轨迹，未通过环境重放验证行为因果或后续学习收益。
