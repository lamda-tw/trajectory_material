执行轨迹中的伴随信号（仅失败题）：

- 上下文窗口错误：24/117 题；其中为 3000 输出 tokens 预留不足 13 次，输入本身超过 32000 tokens 11 次。这些任务仍由官方 evaluator 计为失败，但错误发生在模型无法接收过长上下文时。
- 上下文错误的 24 题均未完成提交，且均伴随答案不匹配条件；在 38 题答案不匹配中，14 题没有上下文错误。未出现 complete_task 的 29 题中，仅 5 题不伴随上下文错误。
- 上下文错误按难度分布：1 级 2 题、2 级 5 题、3 级 17 题。
- Python 执行错误：失败题 93/117，成功题 25；错误本身并非必然导致失败，关键还要看后续是否修复。
- 达到 50 步上限：5/117 题；未出现 complete_task action：29/117 题。
- 无可执行代码 observation：0/117 题、0 次。
- content=null：0/117 题、0 次；输出长度截断：1/117 题、3 次。

当前最值得验证的改进方向：

1. 优先处理上下文窗口：本次 32000 context 需同时容纳提示与 3000 输出预算；针对长任务，在 train/dev 上比较安全截断、结构化状态压缩与更长的推理窗口，把上下文错误从模型能力失败中单独统计。
2. 针对业务状态未完成：在训练任务上构造“查 API 文档—执行动作—查询最终状态—核对约束”的闭环轨迹，并用官方 evaluator 或局部状态检查奖励训练，而非只模仿成功代码。
3. 针对未伴随上下文中断的答案错误：增加答案提取、证据绑定与提交前复核；先排除前序状态错误，不能把全部 answers match 失败归咎于答案格式。
4. 针对 Python/API 调用错误：补充参数不匹配、分页、鉴权与异常恢复的探索轨迹；优先训练能读取错误反馈后修正调用的能力。
5. 针对长程任务与步数耗尽：在训练集上测试分解计划、进度状态摘要、子目标验证与提前终止策略，重点看难度 2/3 的改进，不只优化简单题。
6. 所有新训练、奖励设计和超参选择只用 train/dev；test_normal 保持最终盲测，不可把本次失败轨迹或 evaluator 私有信息回流到训练。

这些是由失败分布提出的实验假设，不是单次评测可证明有效的方案；应以同协议 Dev 消融和之后独立测试验证。

## 协议与比较边界

- 与刚完成的 Dev LoRA 评测保持同一适配器、ReAct agent、温度 0、seed 100、每题最多 50 步、单次最多 3000 输出 tokens、vLLM 32000 context；仅换为 test_normal。
- 本次不启用 reasoning parser，以保留非 thinking SFT 格式的代码正文，并把 null reasoning_content 兼容成空字符串。
- 历史基座 test_normal 结果启用了 deepseek_r1 reasoning parser；虽是同一 168 题、agent 与 evaluator，但输出协议不同。因此上述基座差值不是纯粹的权重/LoRA 因果消融。
- 逐题原始交互与 evaluator 证据含测试环境数据，保留在本地实验目录，不将其复制进本报告。
