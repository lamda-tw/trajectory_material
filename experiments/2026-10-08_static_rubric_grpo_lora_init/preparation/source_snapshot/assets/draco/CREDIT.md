# Credit assignment

Applies to the three settings whose reward mode is `rubric_credit`: static + credit,
dynamic + credit, and self-judge dynamic + credit.

## What it does

GRPO produces one scalar advantage per trajectory. If that scalar is spread uniformly over the response tokens, every
token of a 50-turn AppWorld rollout is pushed equally hard — including the turns that had
nothing to do with why the rollout succeeded or failed.

Credit assignment redistributes that same advantage across the trajectory's steps, so steps
the judge held responsible for an outcome move more, and steps it did not move less. The
total gradient mass for the trajectory is unchanged. This is redistribution, not rescaling.

## Pipeline position

Credit assignment is the last stage of the rubric reward pipeline. The stages before it are
documented in full in [REWARD_PIPELINE.md](REWARD_PIPELINE.md); in brief:

| Stage | What happens | Where |
|---|---|---|
| 1 | Candidate rubrics are obtained — read from the static file, or generated by the judge per rollout | `rubric_reward.py` |
| 2 | **Union** (dynamic mode only): the group's six candidate rubric sets are merged by the judge into one shared set, so every member of the group is scored against identical rubrics | `rubric_reward.py`, prompt [`rubric_prompts/union_rubrics.txt`](../src/verl_appworld/rubric_prompts/) |
| 3 | The judge returns a PASS / NOT-APPLICABLE / FAIL verdict per rubric per trajectory | `rubric_reward.py`, prompt [`rubric_prompts/score_rubrics.txt`](../src/verl_appworld/rubric_prompts/) |
| 3b | **Rubric dropout**: a rubric is dropped from the reward denominator unless at least one member of the group failed it. A rubric everyone passes cannot separate good rollouts from bad, so it only dilutes the ones that can. All-FAIL rubrics are kept — that is real signal | `_non_discriminative_indices` in `rubric_reward.py` |
| 4 | Reward = mean verdict over the surviving applicable rubrics, times a scale (default 10.0) | `rubric_reward.py` |
| 5 | **Credit assignment**: the judge is asked, per rubric outcome, **which trajectory steps were causally responsible**; the citations become a per-step quality score | [`src/verl_appworld/credit_assignment.py`](../src/verl_appworld/credit_assignment.py), prompt [`rubric_prompts/credit_assignment.txt`](../src/verl_appworld/rubric_prompts/credit_assignment.txt) |
| — | Those scores rewrite the per-token advantages | [`src/verl_appworld/credit_advantage_patch.py`](../src/verl_appworld/credit_advantage_patch.py) |

Stages 2 and 3b both need the whole rollout group, which is why the pipeline has a group
barrier.

The final step works by monkey-patching verl's `compute_advantage`. It is installed only
when `APPWORLD_REWARD_MODE=rubric_credit`, and is a no-op otherwise. The rollout loop and
the rest of the trainer are untouched, so the credit settings differ from the non-credit
ones by exactly this one substitution.

## Step quality

Stage 4 yields a quality `Q(S_j)` in `[0, 1]` for each step the judge cited. Steps it cited
for no rubric outcome are marked **uncited**, carrying a sentinel value of `-1.0` — chosen
because it is outside the valid `[0, 1]` range and so survives being passed through numpy
object arrays and JSON without being mistaken for a real quality.

## Turning quality into a per-token advantage

Let `A_i` be the trajectory's GRPO advantage. Each step gets a weight `w_j`, and the sign of
`A_i` decides how quality maps to weight:

```
winning trajectory (A_i >= 0):   w_j = Q_j          reward the steps credited for the success
losing  trajectory (A_i <  0):   w_j = 1 - Q_j      punish the steps blamed for the failure
```

An uncited step takes the **mean quality over the cited steps** as its quality before that
mapping is applied. So an uncited step is treated as an average step, not as a bad one.

The per-token advantage for token `t` inside step `j` is then:

```
a_it  =  A_i * N_steps * w_j  /  ( n_j * Sum_k w_k )
```

where `n_j` is the number of tokens in step `j`, and `N_steps` is the total number of tokens
that fall inside any detected step.

Two properties follow, and both are deliberate:

- **The step's total pull depends only on `w_j`, not on `n_j`.** Summing `a_it` over the
  tokens of step `j` cancels `n_j`. A verbose step therefore earns no more gradient than a
  terse one of the same quality. This is what makes the scheme length-normalized, and it is
  why the formula is not simply `A_i * w_j` per token.
- **The total is conserved exactly:** summing `a_it` over all credited tokens gives
  `A_i * N_steps` — the same mass GRPO assigned. Credit assignment moves gradient between
  steps; it never adds or removes any.

## Gap tokens

Not every response token belongs to a step. Turn glue, tool-result echoes, and formatting
between steps fall inside no detected step span. These are **gap tokens**.

Gap tokens are handled as follows:

- They receive a per-token advantage of exactly **0.0**. They are not pushed in either
  direction.
- They are **excluded from the budget denominator**: `N_steps` counts only tokens inside a
  detected step.

The second point is what makes conservation exact and independent of how many gap tokens a
trajectory happens to contain. If gap tokens were counted in the denominator, a trajectory
with more turn glue would silently dilute the gradient on its real steps, and two
trajectories with identical step qualities would train differently based only on formatting
overhead. Every real response token is written by the reallocation — step tokens get their
share, gap tokens get zero — so no token is left holding a stale value.

## When credit assignment declines to act

The reallocation returns "no usable credit" and the raw advantage `A_i`, spread uniformly over the response tokens, is used instead, in
two cases:

- **No step was cited at all.** There is no rubric evidence to redistribute on, so the
  trajectory falls back to standard GRPO behaviour.
- **Total step weight collapsed to ~zero.** For example a winning trajectory whose only
  cited steps all have `Q = 0`. Dividing by that sum would be numerically meaningless, so
  the trajectory falls back rather than producing a degenerate result.

Both are silent fallbacks to correct baseline behaviour, not errors. But they do mean a run
can be "working" while credit assignment is doing nothing on a subset of rollouts — check
`credit_calls.jsonl` rather than assuming.

## Configuration

| Variable | Default | Effect |
|---|---|---|
| `APPWORLD_CREDIT_NEUTRAL_Q` | `0.5` | Quality assigned to a step with no citation signal, in the stage-4 scoring code |
| `APPWORLD_CREDIT_UNCITED_FLOOR` | `0.0` | Floor on the quality base used for uncited steps: `max(mean_cited_Q, floor)`. At the default the mean is used unmodified |
| `APPWORLD_CREDIT_W_FLOOR` | `0.0` | Additive floor on every step weight: `w_j = floor + w_j`. At the default, weights are purely multiplicative, so a step with weight 0 receives no gradient at all. Raising it guarantees every step some minimum share |

All three defaults reproduce the behaviour used for the results in this repository. Leave
them unset unless you intend to change the algorithm.

Credit assignment tokenizes each step to find its token span, and takes the tokenizer from
`MODEL` — the same weights the run trains. `APPWORLD_MODEL_PATH` is read only if `MODEL` is
unset, which a launcher never leaves unset.

Which revision of these two modules a run actually loads is worth being sure of, because
installing a different one is a wrong-algorithm run rather than a visible failure: the run
trains, and only the numbers are wrong. `setup.sh` compares every staged file byte for byte
against this checkout and refuses to finish on a mismatch, so the code a run reads is the code
you are reading.

## Verifying it works

Per-rollout inputs and outputs are logged to `runs/<RUN_TAG>/percall_logs/credit_calls.jsonl`.
Each row carries the judge's citations, the derived `step_qualities`, and the step token
spans.

The conservation property gives a cheap correctness check: for any rollout, the sum of
per-token advantages over credited tokens must equal `A_i * N_steps`. If it does not, the
step spans failed to line up with the tokenization.

That is a real failure mode. The patch locates step boundaries by decoding the response and
re-tokenizing it, using a tokenizer loaded from the model path. If that tokenizer fails to
load, the code caches the failure and **skips credit masking for the batch** rather than
crashing — which means a misconfigured model path produces a run that looks healthy while
silently training as though credit assignment were off. Check the logs for the skip.
