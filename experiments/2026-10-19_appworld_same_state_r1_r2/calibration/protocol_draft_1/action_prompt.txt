Auxiliary rubric definitions (frozen English v7 source):
R1 Execution Validity: Check whether the syntax, variables, APIs, arguments, types, and authentication in the actual code support normal execution. Assign F for an execution exception or termination caused by the absence of executable code; assign P for normal execution. A syntax error usually prevents the entire block from executing, whereas a runtime error may occur after some operations have already taken place. Successful execution does not guarantee correctness with respect to the task.

R2 Evidence and Coverage: When gathering or using evidence, check sources, objects, details, and scope against the current task-relevant subgoal. Assign P for valid local reads, pagination, and filtering; assign N when there is no evidence gathering or judgment about evidence, or when only execution fails. When claiming or relying on "all," "maximum," or "unique," check the evidence set: F for known omissions, irrelevant inclusions, or mismatched object relations; U for unresolved relevance, duplication, or time range. Judge pagination only from visible specifications or feedback; filenames and summaries do not establish unread content. Intermediate evidence gathering is not responsible for global conclusions that have not yet been made, and unknown conditions from other steps do not automatically carry over to this dimension.

R3 State and Data Fidelity: Check this step's concrete factual claims and the data, field meanings, object identities, and states actually used. Assign F for contradicting visible evidence, fabricating data, confusing objects, treating an old snapshot as current state, or claiming an unexecuted action has been completed. Assign U for necessary facts that cannot be verified. Plans, search leads, and hypotheses explicitly awaiting verification are not established facts. Assign N when there is no factual claim or data interpretation. Supported literal values are allowed; syntax, type, and argument errors alone do not automatically make this dimension applicable.

R4 Decision Logic and Calculation: Evaluate actual task choices, combined conditions, exclusions, aggregations, times, amounts, and units. Assign F for a clearly incorrect rule or treating an unsupported assumption as a basis for a task decision; assign U when the rule is correct but necessary facts are unknown. Assign N for documentation lookup, authentication, API fixes, data retrieval alone, and plans that have not formed a concrete decision. Assign P for correct intermediate calculations. Coverage and delivery issues from presenting a subtotal as the complete answer are evaluated separately.

R5 Actions and Actual Effects: Evaluate actual local task-related modifications against applicable task constraints on objects, content, scope, and preserved state. Assign N for reads, calculations, documentation lookup, authentication preparation, or complete_task alone. Also assign N when this step is rejected by authentication, argument, or precondition validation before any task-related modification occurs. Assign F for clearly wrong objects or content, or effects known to violate the goal; assign P when local effects are sufficiently supported; assign U when necessary effects or goal conditions are unknown. An incorrect selection rationale alone does not establish that the effects are wrong. Arguments that permit overwriting or deletion do not establish that damage has occurred.

R6 Feedback and Recovery: This dimension applies to existing errors, contradictions, invalid results, or repeated queries and operations. Assign N for normal first-time progress or the first occurrence of an error. Assign P for repairs or new evidence addressing an identified problem or verification need, even if an independent new error occurs. Fixing an execution problem does not cancel task-related errors under R3-R5. Assign F for ignoring feedback, repeating known errors, or repeating queries without new information or a need for verification. Compare the current state with what was actually executed: refreshing state and skipping already completed work can be valid recovery. Do not assign F solely because code is identical or a potential defect was not triggered. After a compound write fails, assign F for repeating writes that may cause conflicts or duplicate side effects without checking for partial success.

R7 Termination and Delivery: On submission or completion claims, check the required answer (content, format, or no answer) and evidence that required operations are complete. Assign F for a known incorrect answer, claiming completion without performing necessary operations, or missing a required deliverable; assign U when necessary completion evidence is unknown; assign P when evidence is sufficient. Unknown task-critical conditions require new evidence; a valid answer or successful submission cannot turn them into P, nor can missing verification alone turn them into F. Assign N to intermediate steps. An honest failure report may receive P, but this means only truthful termination, not task success. A budget interruption does not automatically make the last normal action wrong. Failure to check API specifications is evaluated only under R8.

R8 Authorization and Interaction Protocol: Check permissions and API, code-block, and environment constraints explicitly specified in the input; do not add requirements. When complete API specifications must be checked before use, this also applies to complete_task; summaries, examples, or successful calls do not substitute for specifications. Complete specifications already provided may be reused; documentation lookup entry points provided in advance are exempt from the prior specification lookup requirement. When one code block per step is required, additional nonempty code blocks in commentary also violate the requirement, even if only the first block is executed. Evaluate answer content and delivery format under R7, and API, code-block, and environment constraints under this dimension. A protocol violation does not automatically establish that a task conclusion is wrong.
