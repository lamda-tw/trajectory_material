# 纯 ZeroFail3 SFT：第三轮退化与续训正确性核验

审计时间：2026-10-26T16:53:53+08:00。完整训练统计覆盖第 1–3 轮；第四轮仅统计已提交的第 55–59 批。第 60 批仍在运行。此次仅进行 CPU 读取和统计，没有重跑评估、启动新训练、修改运行中的配方或中止既有训练。

**结论：恢复链路没有发现错误，第三轮的能力退化是真实且明显的。** 模型从第二轮 dev57 的 12 题成功降到第三轮的 2 题成功，主要表现为大量重复查询 API 文档、很少继续执行业务操作。应区分“程序正确恢复了训练”与“延长这套训练能提高任务能力”：前者通过核验，后者目前被第三轮结果否定。

## 续训是否接错

核验发现以下事实：

1. 第 37 批采样服务实际加载的是原纯 SFT 第 36 批 student LoRA；第 37 批训练恢复的也是同一完整检查点。运行时代码逐张量检查了 student 权重和 Adam 状态与保存值完全相等。
2. 第 37–59 批的检查点父子哈希、采样模型身份、dataset 身份、优化器计数均连续。第 37 批从 Adam step=36 更新到 37；直接用 CPU 重新打开第三轮完整 state.pt，504 组 Adam 状态全部为 step=54。没有发现回到初始模型、错加载混合模型、重置优化器或重复提交更新。
3. 第二、三轮完整 state.pt 中的 student 权重与导出的 safetensors LoRA 逐张量相等；所有 Adam 状态有限。第三轮评估服务日志确认加载 batch_054 的 student LoRA。评估配置、57 题名单和实际轨迹身份一致。
4. 学习率从第二轮末到第三轮始终是 5e-5，没有重新 warmup。原实现是前 5 次有效更新 warmup，之后保持常数，并非第二轮结束前衰减到零；延长总轮次没有重算或抬高学习率。
5. SFT loss、构建数据、Codex 评分和 rollout 核心脚本与原两轮版本字节相同。训练脚本差异是恢复审计和断言，没有改变梯度计算。配置只变更实验名称、输出路径指向及总轮数/更新数。train90、dev57 内容相同；每轮仍是 90 题，每批 5 题、每题 1 条完整新轨迹，18 次更新。
6. 截至第 59 批，SDPO 样本数、SDPO loss 和 SDPO 梯度均为 0。保留 teacher 状态用于格式兼容不会产生教师前向或蒸馏损失。这里是纯 LoRA SFT，r=8、alpha=16，基础模型冻结。
7. 检查了 89 个冻结依赖、295 条训练轨迹、171 条评估轨迹及官方报告；7,625 个训练步骤的标签全部与原始 Codex 评分逐项一致。所有入选步骤满足 F=0、P>=3。中间检查点删除有对应保留记录；第二轮和第三轮完整模型均仍在。

这些核验足以排除当前最直接的恢复错误与评错模型问题；它们不能证明训练目标本身适合长时间优化，也不能替代多种子或受控消融。

## 为什么 loss 下降，能力反而下降

本实验是在线自采样筛选 SFT：每轮都用当前学生重新采轨迹，Codex 判断哪些步骤可以模仿，再学习这些步骤。它不是反复训练同一份固定专家答案。

| 入选训练样本/训练数值 | 第1轮 | 第2轮 | 第3轮 |
|---|---:|---:|---:|
| SFT 步骤数 | 311 | 650 | 1198 |
| 其中纯文档步骤 | 201（64.63%） | 411（63.23%） | 731（61.02%） |
| 其中业务 API 步骤 | 43（13.83%） | 109（16.77%） | 160（13.36%） |
| 其中重复文档步骤 | 4（1.29%） | 12（1.85%） | 33（2.75%） |
| 入选步骤平均回答长度 / token | 71.81 | 65.82 | 44.77 |
| 每批 SFT loss 的轮内平均 | 0.1106 | 0.0998 | 0.0607 |
| 裁剪前梯度范数范围 | 0.205–0.440 | 0.192–0.468 | 0.305–0.523 |
| 发生梯度裁剪的批数 | 0/18 | 0/18 | 0/18 |


**最有证据支持的解释是长期学习目标偏向了查文档等局部合规动作。** 查文档通常容易同时通过 R1（执行）、R2（有效读取）、R8（交互协议），因此能满足 ZeroFail3；这不等于对最终完成任务产生了同等价值。三轮中查文档一直占入选样本约 61%–65%，并非第三轮该比例突然跳高。业务操作只占 13%–17%。持续优化同一目标后，模型越来越倾向选择文档动作，是与现有现象一致的机制推断，尚未通过限额采样等消融确证。

按当前 loss 定义，每个步骤内部先做 token 平均，再在一批内对步骤平均。因此很短的文档步骤也有完整的“一个步骤”的权重；第三轮各批文档步骤的平均系数占比约 61.36%。这不等于实际梯度范数贡献也占 61.36%。第三轮入选样本更多，也不等于优化器更新翻倍：每轮始终只有 18 次更新。

**过滤 FAIL 不等于教会模型避免 FAIL。** 第三轮采到的 886 个重复文档步骤中，仅 33 个进入 SFT，853 个（96.28%）被屏蔽。33 个重复步骤不一定都是误判：rubric 允许为新错误或验证需求重新查阅，不能只凭代码相同认定违规。因此，“把大量违规循环直接当正确答案训练”并不受数据支持。更值得担心的是：其余 731−33=698 个非重复文档步骤被持续强化，而屏蔽错误步骤没有提供明确的反循环训练信号。

loss 降低表示更容易拟合当前筛选出的回答，不表示更会完成任务。这里每轮训练样本都在变化，平均回答还从约 66 token 缩短到 45 token；轮间 loss 不能当作同一份验证集上的能力曲线。第三轮梯度范数约 0.305–0.523，无 NaN/Inf、无裁剪；没有发现学习率重启或数值爆炸造成掉分的迹象。第四轮第 58 批有一次范数 2.396，按原配置裁到约 1.0，发生在第三轮评估之后，不能解释第三轮掉分。

## 为什么看上去是第三轮突然坏了

正式 dev57 每轮只评一次，因此无法定位某一次参数更新之后立即崩溃。但训练轨迹显示：

| 训练区间 | 纯文档占所有生成步骤 | 重复文档占所有生成步骤 |
|---|---:|---:|
| 第二轮末6批（31–36） | 48.36% | 22.78% |
| 第三轮前6批（37–42） | 46.83% | 23.54% |
| 第三轮中6批（43–48） | 48.74% | 21.40% |
| 第三轮后6批（49–54） | 73.10% | 46.29% |
| 第四轮前5批（55–59） | 70.90% | 39.78% |

这些区间题目不同、训练采样 temperature=1，不能当作同题因果对照。但恢复后的前几批并未显示与续训边界同步的文档行为突变，第三轮后段明显更重。更合理的描述是“训练过程中逐渐偏向文档动作，轮末评估揭示严重退化”，而不是“刚恢复就恢复错了”。固定 5e-5 可能使这种偏向继续积累，但尚无降低学习率的对照，不能断定学习率是唯一原因。

## 具体案例

**b119b1f_2：播放到指定歌手。** 第二轮 17 步完成，检查 6/6：查必要文档、登录、反复执行 next_song 并检查当前歌曲，然后结束。第三轮 29 步全部在查文档，没有真正执行业务 API；第 5 步查 search_songs 文档、第 6 步查 search_artists 文档，随后第 7–29 步在两份文档之间来回重复，最终上下文超限，检查 0/6。这里“连续完全相同文档”的长循环指标会漏掉交替循环，所以必须看重复文档占比。

**d4e9306_2：关注喜欢的歌曲/专辑对应歌手。** 第二轮 17 步、检查 6/6，在第 14–16 步实际执行 follow_artist。第三轮完成登录后，第 9–14 步读取多份相关文档，第 15–50 步全部重复查这些已经读过的文档，没有执行关注操作；36/50 步是重复文档，触及 50 步上限，检查只剩 1/6。

**6c2c621_1：导出笔记。** 第二轮 20 步、检查 6/8，已经存在内容遗漏但仍执行了部分业务；第三轮变成 50 步、37 个重复文档步骤，检查仅 1/8。退化不是只影响某一个 Spotify 接口。

## 对原判断与后续安排的修正

原来“两轮预算内纯 SFT 优于混合和纯 SDPO”的数据结论仍成立；但不能据此推断“SFT 不会退化、问题只在 SDPO”。第三轮已经证明：没有 SDPO 也会出现同类文档循环，因此 SDPO 不是这种退化的必要条件。此前混合与纯 SDPO 更早、更重的退化仍值得解释，但当前需要同时审视共同的在线自采样、rubric 筛选和动作分布。

当前依照既有授权继续第四、五轮，不擅自改变学习率、筛选规则或模型，以保留原定续训对照的含义。第四、五轮尚无正式结果，不能预判一定恢复或一定更差。第二轮完整检查点保留；目前应视其为已评估轮次中最好的候选，而不是默认采用最后一轮。继续到五轮的价值转为确认退化走势，而非已有证据支持“越训越好”。

若后续轮次未恢复，下一步优先考虑从第二轮开展小规模、单因素诊断：限制文档动作在 SFT 中的采样权重、提高有效业务推进步骤的比例；分别检查固定训练样本与在线重采样的差别。降低学习率可作为独立对照，不能同时改动多个因素后宣称解决了根因。此次没有启动这些新实验。
