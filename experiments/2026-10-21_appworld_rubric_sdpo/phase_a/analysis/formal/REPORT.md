# 阶段 A 正式结果与进入 B 的判断

分析日期：2026-10-22，Asia/Shanghai。自动实验于 20:15:35 完成。本报告使用正式集，不把 8 个调试状态混入统计。参数更新为 0；阶段 B/C 均未启动。

**结论：具体 Codex 反馈明显改善冻结 Qwen3-8B 的单步局部修复；完整附上原回答在当前模板下总体有害。这个方向值得继续，但原版 B 尚未满足事先设定的全部绿灯条件。建议先补充短续跑和蒸馏信号检查，再决定是否做小规模 B；不直接启动原错误前缀上的混合训练。**

本报告的“修复”指预定 LR，不是 AppWorld 任务完成率，也不是已经获得训练收益。A 检验了一个带反馈的冻结模型能否给出更好的动作，尚未检验不带反馈的学生经过训练后能否迁移这种能力。

**条件与指标**

| 条件 | 新动作生成时提供的上下文 |
|---|---|
| C0 | 原始任务、指令、动作前历史 |
| C1 | C0 + 原目标步的 FAIL 规则标签/名称提醒 |
| C2 | C1 + 具体 diagnosis 和 correction |
| C3 | C2 + 完整原回答 |

候选各自从相同动作前状态开始，只执行一步。完整原轨迹在生成前统一评分；候选执行后使用未改动的原 v7 离线评分，没有在 agent 的动作循环中同步调用 Codex。

LR=1 要求候选 R1=P、八维无 F、原来含 F 的维度均变 P/N，不能变 U。严格 LR 另要求全部维度无 U。把失败动作换为必要的首次文档查询可以得 LR=1，但不能据此声称原业务目标已经完成。特别是 F→N 可能意味着当前动作退回前置准备，旧业务问题仍需后续解决。

具体反馈的有效部分是给出“哪里错了、依据是什么、下一步如何取得缺失证据或修复代码”。单给 R1/R6/R8 名称往往不足以让 8B 自己定位原因。固定样本中的例子：

- `state_9ac003937b88afdd`：原代码先生成布尔列表，再对第一个布尔值索引 password，造成 TypeError。C0/C1 的四次候选均重复错误；C2/C3 的四次候选都改成先筛选 phone 账户记录、再提取 password。这里有直接代码级修复，不只是查文档。
- `state_74151614143520ad`：原代码把整个登录响应当 token，并用 page_limit=100。C2 两次改用真实 token 字符串与 20 的分页上限，得到交易列表；C3 两次分别卡在虚构 get_contacts 或再次使用错误 token。C2 的年份仍硬编码，身份过滤和求和未完成，故只确认认证和读取有推进。
- `state_e444490e2ca9ab14`：C0/C1 四次重复已有的 phone API 列表；C2/C3 转为首次读取 phone.login 完整规范，获得正确认证所需信息。这是合理的错误恢复前置步骤。
- 反例 `state_a29c86f563a8f8b8`：反馈明确说不要再读已知 keys，C2 两次仍执行 `album_songs[0].keys()`，继续 R6=F。反馈并非对所有状态都能突破循环。
- 反例 `state_1abe92d466de6d33`：C2 获取密码来解决未定义 token，确有准备作用，但忘记先查 Supervisor 规范，仍 R8=F。局部修一个错可能引入/保留另一个错。

**修复是否只是少做事**

C2 的 198 个 FAIL 候选中，147 个只调用文档 API；149 个 LR 成功中，**131 个（87.9%）只调用文档 API**。其平均业务 API 调用从 C0 的 1.60 次降到 0.32 次（排除 api_docs 和 supervisor），数据库变化只有 1/198，未调用 complete_task。没有空代码候选、没有输出长度截断，故不是靠输出空白或提前宣告完成得分；但一步诊断确实偏向“先补规范、先验证”的准备动作。

固定复核的 16 个 FAIL 状态、每条件 32 个候选中，LR 计数为 C0=6、C1=4、C2=25、C3=20。助手判断 C2 的 25 个 LR 成功中，24 个有相关文档/信息/局部执行准备上的进展，1 个是重复查询（`state_76557df73339f33c` 的 C2 repeat0 重读第2步已有的 show_song_library 规范）。另有 C1 重读 API 列表却通过的案例，以及干净对照重读初始参考规范却通过的案例。它们说明 v7 的重复检测仍有误差；原标签全部保留，不据助手观点改写自动分数。

因此不能把查文档一概视作逃避工作；多数是必要的前置修复。但不能把这种改善直接换算成完成任务的收益。单步之后是否会正确应用规范、跳出循环并完成任务，A 未测。

唯一 C2 数据库变化来自 `state_f2113e2add2bf460`：模型刷新 pending payment requests 后批准了 5 条请求，却没有验证请求者是否属于目标关系集合。自动评分为 R4=F、R5=U，LR=0。没有证据据此断言 5 条都是错误付款，但也绝不能把“C2 没有 R5=F”解释为写操作均正确。这个案例在后续多步验证中应重点检查。

**带完整原回答是否有帮助**

当前结果支持默认采用 C2。C3 总体损失 11.71 pp；劣势主要在 recovery（−20.83 pp）和 protocol_only（−24 pp），semantic 点估计 +2 pp，不足以建立该子集的稳定收益，也不支持“原回答永远有害”。

支持旧答案锚定的证据包括：执行报错由 C2 9/198 增至 C3 21/198；重复原代码由 24 增至 31；R6=F 由 30 增至 42；R8=F 由 26 增至 40。`state_f740d80012bc085e` 中，C2 两次先读 create_playlist 规范，C3 两次照搬旧创建代码，虽实际创建了列表却再次违反先读规范的约束。

该对比测量的是“完整原回答＋当前提示模板”的整体效果，不能严格分离复制倾向、上下文长度和措辞影响。所有候选均未因输出上限截断，且所有 99 个 FAIL 四条件配对完整。更短的错误片段、结构化错误位置等没有做过，不能由本实验判定其效果。

**教师分布：A 对 SDPO 的支持有边界**

以下都是在同一原回答 token 前缀上，比较无反馈学生与不同反馈教师，先平均每回答 token、再平均 99 状态。单位为自然对数。它们不是训练梯度测量。

| 条件 | 原回答平均 token log-prob 相对 C0 | 全词表 KL(student ‖ conditioned) | 原回答平均 log-prob 上升的状态 |
|---|---:|---:|---:|
| C1 | −0.1014 | 0.1071 | 6/99 |
| C2 | **−0.3494** | 0.3569 | **0/99** |
| C3 | −0.0931 | 0.6671 | **33/99** |

C2 对整段原回答的平均 log-prob 在全部状态都下降，方向有吸引力；C3 有 33 个状态上升，吻合保留旧答案的风险。不过 **KL 更大不是教师更好**，全回答平均下降也不证明每个错误 token 的训练信号正确。

只有 15 个状态有“真实 traceback 确认＋诊断明确提及＋可对齐”错误表达式；这是少量、偏向执行错误的子集，不代表全体语义错误。表达式所有出现位置可能包括说明文字，因此逐例检查范围，不能称为人工错误 token 金标。C2 的表达式平均 delta：9 个负、5 个正、1 个零，其中有接近浮点零的变化；C3 为 3 负、10 正、2 零，不能机械按正负符号判所有样本。

两个代码位置证据特别清楚：

1. `state_892f4749a5dc63b7`：在已经知道 songs 是 dict 的原代码位置，`.extend` 的条件概率为 C0 **35.02%**、C1 **4.02%**、C2 **0.093%**、C3 **85.19%**。C2 强烈压低该错误续写，C3 反而提高。更值得注意的是，这个状态 C3 两次重新生成候选都 LR=1，证明“生成纠错成功”与“在旧错误前缀上的分布可靠”是两件事。
2. `state_ef628380f92aeabc`：原代码调用不存在的 `supervisor.get_contact_email`。在强制给定旧代码前缀后，`_contact` token 概率由 C0 **18.23%** 上升到 C2 **99.98%**，`_email` 从 **66.80%** 上升到 **99.999%**。这是 C2 也会保留明显错误续写的反例，不能用全回答 log-prob 下降掩盖。

合理解释是：原错误思路/代码前缀被 teacher-forcing 固定后，模型可能继续补全那条错误路径；反馈中提到错误 API 本身也可能产生提示效应。当前数据不能分离这两个机制。对应 KL 会将学生分布推向该教师分布，但参数共享、其他 token 和 SFT 项会影响净更新，**未运行反向传播，不能直接断言实际训练必然提高该错误率**。

数值边界：全部自身 KL 为零，token 对齐通过；与历史 vLLM log-prob 的每状态平均绝对差，均值 0.00573、最大 0.02451，存在后端/精度差异。学生 top-100 平均概率质量的状态最小值为 0.9999738。top-100+tail 用 fp32 的 `1−mass` 计算极小尾概率，近零时会有舍入；解释以保存的全词表 KL 和清楚的单 token 概率为主，不把极小 tail 的差异当机制证据。

**干净对照与评分可靠性**

25 个干净状态的 C2 是固定中性消息：“记录的下一动作未发现违规，这不证明任务完成；按原指令选择下一动作。”它不包含具体负反馈，也没有执行记录中的下一动作。

C0 的可执行且无 F 比例为 **34/50=68%**，中性 C2 为 **31/50=62%**，配对差 **−6 pp，95% CI [−22, +8]**。5 个状态改善、13 个持平、7 个变差。这个样本不足以证明退化，也不足以证明无害；点估计已超过预定 5 pp 风险门槛，不能事后改门槛使实验“通过”。

这项结果测的是上下文扰动，不是模型训练后遗忘，也不是向好步骤发负反馈的效果。`state_7bc3a64991ff9ad7` 中 C0 两次完整分页读歌单，中性 C2 一次把 page_limit 提到 100 导致报错；另一些对照则改善。因此后续 F=0 步骤宜维持原 SFT 输入，不必加入无必要的诊断消息；这不能消除混合训练可能带来的间接退化，仍须最终评估。

自动评审移除了条件名和反馈提示，但模型自己的 commentary 有时说“based on feedback”，未从真实轨迹中删除。关键词检出的 FAIL 候选为 C0 0、C1 52、C2 49、C3 59，因此不能称为完全盲评。相同完整公开输入（仅忽略匿名 trajectory_id）的 49 个重复组、105 条候选中，8 组有某维标签差异，**0 组 LR 不一致**。这支持本次主指标的局部稳定性，但不等于独立验证裁判正确性。

推荐把下一步定位为 **A+ 补验证／B 前的技术准备**，不把当前结果直接标记为原版 B 绿灯。以下仅是建议，本轮没有运行：

1. **固定短续跑验证。** 对事先固定、覆盖四层的状态，从 C0/C2 修复候选之后再续 3–5 步，统一离线评分。采样名单、预算和停止条件先冻结，纳入失败、协议修复、文档重复和付款身份未核实案例；不要只挑本轮 C2 成功样本。记录规范是否被应用、是否再次循环、是否形成有依据的业务读写；仍不把 3–5 步当作完整任务 TGC。
2. **先核实损失信号，再选择 B 版本。** 保留上述 `.extend` 和 `get_contact_email` 作为明确反例，比较原回答前缀下的 C2 教师与独立生成、验证过的修复回答路径。若考虑用修复候选做正向监督，应明确这是修复轨迹蒸馏/SFT 的新分支，不冒充原来定义的学生 on-policy KL。即使改用新学生动作采样，仍须检查旧错误前缀锁定现象，不能假设它自动消失。
3. **保留 C2，暂不把 C3 纳入主训练分支。** 原版 B 的在线 v7-ZeroFail3 SFT 对照有必要；混合分支的 FAIL 信号形式应在上述检查后冻结。F=0 步骤继续原输入，不附中性诊断；F≥1 才使用有证据的反馈。不能直接把失败原回答当正向 SFT 标签。
4. **若随后启动小规模 B，沿用可归因的基本结构。** 每批5题各1条完整轨迹、同一学生版本采样、结束后整轨迹评分、累积完选中步骤再更新一次；两个分支同起点、同任务顺序和预算。A 没有测过梯度，不能从本结果推出 λ=1、lr=5e−5 或 EMA=0.95 已经合理；这些仍是原计划候选值，需要单独数值/梯度调试与参数更新授权。最终比较不带反馈的学生，并保留任务完成指标及对照退化检查。

本轮完成状态检查、统计审计、固定样本助手复核及报告，不进行新模型采样、GPU计算、参数更新或 B/C 启动。
